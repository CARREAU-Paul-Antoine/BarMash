RAPPORT D'AUDIT DE PERFORMANCE

BarMash

Moteur de simulation temps réel en Go — 10 000 agents, 30 ticks/s

PÉRIMÈTRE DE L'AUDIT

BarMash simule une soirée dans un bar : 10 000 clients se déplacent vers 8 comptoirs, boivent, se bousculent et laissent des flaques qui ralentissent leurs voisins. Le serveur calcule un tick toutes les 33,3 ms et pousse l'état complet au navigateur par WebSocket.

L'audit part de la version naïve livrée, mesure ses goulots réels, puis applique et vérifie une série d'optimisations. Chaque étape est validée par une empreinte bit à bit de l'état de la simulation : le comportement fonctionnel n'a pas changé d'un octet.

4. Tentatives infructueuses et reproductibilité

BarMash • Audit de performance

Échec n°1 — Rejet par boîte englobante écrit avec || : +52 % de temps

Variante (scan de bousculade)earlyrush
Avant (séparation chaud/froid seule)1,40 ms—
if ndx >= 22 || ndx <= -22 { continue }2,28 ms (+52 %)2,72 ms (+44 %)
if math.Abs(ndx) >= 22 { continue }1,14 ms (−19 %)1,60 ms
  • Hypothèse : éviter la racine carrée sur les voisins lointains. Mesuré : 97 % des voisins sont éliminés dès le premier test.
  • Cause : le premier saut dépend du signe de dx, qui est aléatoire. Le prédicteur de branchement se trompe une fois sur deux : 600 k voisins × 50 % × ~15 cycles de vidage du pipeline ≈ 0,9 ms, soit exactement l'écart mesuré (+0,88 ms).
  • Correction : math.Abs est un simple masque de bit, sans branchement. Il ne reste qu'un saut, juste dans 97 % des cas. La même condition logique coûte +60 % ou −19 % selon son écriture.

Échec n°2 — O1 : flaques par valeur (gain nul)

  • Hypothèse : les ~450 *VomitPuddle dispersés provoquent des défauts de cache.
  • Mesure : +1,4 % early, +0,6 % rush (p < 0,01).
  • Cause : les flaques étaient allouées à la suite et tiennent en 18 Ko, donc dans le L1d (48 Ko). Le problème était le nombre de tests, réglé ensuite par O2.

Échec n°3 — O8 : struct de 80 o → 48 o (neutre)

  • Hypothèse : tenir clients + positions dans le L2.
  • Mesure : early p = 0,063, rush p = 0,481 → pas d'effet.
  • Cause : les clients sont lus séquentiellement ; le prefetcher suit le flux et l'ancien jeu (960 Ko) tenait déjà en L2. Conservé pour l'empreinte mémoire (−40 %).

Biais de mesure repéré : alignement du code

Après O6, le tick early a pris +2,8 % alors que la boucle n'avait pas changé. Un A/B entrelacé des deux binaires confirme l'écart (p = 0,000), et la comparaison du code machine montre que seuls le padding (NOP) et un pas d'adresse ont bougé : la boucle chaude a été réalignée. C'est un effet de placement du code, pas un effet algorithmique. D'où la règle suivie ensuite : comparer en A/B entrelacé dès que l'écart attendu est sous ~5 %.

Conclusion

Action la plus rentable : O2, l'index des flaques. À elle seule, elle divise le tick de croisière par 2,95. C'est aussi celle que le profil désignait le plus clairement. Côté réseau, l'encodeur manuel (O6 + O6b) divise le coût d'une frame par près de 10.

Accent mis : d'abord le CPU (algorithmique, puis branchements et racines carrées), puis la mémoire / GC (zéro allocation, flaques et clients sans pointeurs, −40 % sur la struct client). Le serveur tient ses 30 ticks/s avec une marge énorme : 1,3 ms utilisées sur 33,3 ms de budget.

Ce qui n'a pas marché : l'erreur la plus instructive est le rejet par boîte englobante écrit avec ||. Une optimisation « évidente » sur le papier a ralenti le tick de 52 % à cause du prédicteur de branchement. Les deux optimisations purement mémoire (O1, O8) n'ont rien apporté au CPU : dans ce projet, les données tenaient déjà en cache.

Suite : la concurrence n'a pas été traitée. Paralléliser la boucle impose de séparer une phase de lecture (forces, flaques) d'une phase d'écriture pour garder le déterminisme du RNG. Un format binaire pour la frame (~360 Ko de JSON aujourd'hui) réduirait aussi la bande passante réseau.
